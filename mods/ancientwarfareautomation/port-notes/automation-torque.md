# automation-torque: torque energy grid and torque blocks

Slice key `automation-torque`, module `ancientwarfareautomation`. Ported from `automation/tile/torque/**` and the torque
blocks of `automation/block` (report 05). Nothing was compiled; every 1.21.1 / NeoForge name was checked against
`analysis/mc-sources` (see "Unconfirmed API" for the few that rest on other slices' usage only).

## Design decisions (where the port differs from 1.12.2)

- **Metadata tiers are separate blocks.** `torque_shaft`, `torque_junction`, `torque_distributor`, `flywheel_controller`,
  `flywheel_storage` become `<name>_light|medium|heavy` (15 blocks); plus `hand_cranked_generator`, `stirling_generator`,
  `waterwheel_generator`, `windmill_generator`, `windmill_blade` = 20 blocks. The tier is a constructor argument of the block
  (`ITieredBlock`); the tile classes keep the three per-tier classes so the shaft chain test (`getClass()` equality) still works.
- **Facing is the block state property `facing`** (`BlockStateProperties.FACING` for the six-way blocks shaft, junction,
  distributor; `HORIZONTAL_FACING` for the four-way blocks). The tile reads it (`getPrimaryFacing()`), `setPrimaryFacing` writes
  it, so `orientation` is no longer saved. The hammer (Core `HammerItem`) turns any `facing` property, which replaces
  `BlockTorqueBase.rotateBlock` (four-way blocks turn clockwise, six-way ones about the clicked axis). Placement uses
  `BlockRotationHandler.getFaceForPlacement(context, block)` (waterwheel and windmill generator are `invertFacing`).
- **Block entity type without a registry reference.** The base slice declares the registry entries, so the blocks take a
  `Supplier<? extends BlockEntityType<?>>` and the tiles call `IBlockEntityTypeProvider.typeOf(state)` in their super
  constructor. All tile constructors are `(BlockPos, BlockState)`, so `TileTorqueShaftLight::new` is a valid
  `BlockEntitySupplier`.
- **Client animation sync** (the 1.12.2 `PacketBlockEvent` channel) travels as block entity update packets: `TorqueNetwork.sendEvent`
  sends a `ClientboundBlockEntityDataPacket` whose tag holds only an event type and a value to the players tracking the
  chunk; `onDataPacket` of the tiles handles it (types 0 to 5 = side animation percent, 7 = flywheel controller powered,
  1 = flywheel storage energy percent). Late joiners get the full state through the usual update tag
  (`writeUpdateNBT` / `handleUpdateNBT`, same keys as before).
- **Redstone Flux to FE.** `TileTorqueBase.getEnergyStorage(side)` is the receive-only `IEnergyStorage` of a side (null if the
  side neither takes nor gives torque, or `torqueToRf <= 0`); sending uses a `BlockCapabilityCache` of the neighbour's energy
  capability and drains `received * rfToTorque`, as `RFProxyActual` did. Conduit connections attach to any neighbour with an
  energy capability that is not a torque tile (`canConnectEnergy` is gone).
- **Neighbour cache.** Neighbours are found by `instanceof ITorqueTile`, falling back to `AwCapabilities.TORQUE`. The cache is
  cleared by `neighborChanged`/`onNeighborChange` of the block, by `setBlockState` (facing turned), `onLoad`, `clearRemoved`,
  `setRemoved`. Small hardening: a cached neighbour whose block entity was removed (chunk unload) is dropped on use.
- **Multiblock validators.** `MultiblockScan` replaces the recursive `BlockFinder` use: iterative flood fill with a `HashSet`
  (radius 20, same stop rule), bounding box, box test. Blocks are matched by "same block" (tier = block). Flywheel: width
  equal to length and 1 or 3, box full; capacity `width*width*height*perBlockEnergy(tier)`. Windmill: odd height >= 5, one
  extent 1, the other equal to the height, box full (no upper bound, as in the original). Validation is triggered by
  `setPlacedBy` (placed) and by `onRemove` after `super.onRemove` (broken, the block is already gone then), as the
  1.12.2 `onBlockPlacedBy` / `breakBlock`.
- **Water.** The waterwheel's `Material.WATER` tests are `getFluidState().is(FluidTags.WATER)`, the flow strength is
  `LiquidBlock.LEVEL`. Unloaded positions count as "other" (no chunk loading from the 20 tick check).
- **Stirling fuel** is `ItemStack.getBurnTime(null)`; the GUI is left to the GUI slice (hook below).

Small deliberate changes (all local, each also commented in the code):
- Waterwheel: `valid_setup` is now kept in step with the tile (the 1.12.2 block declared it but never set it); the update
  tag is also sent when only the rotation direction changes.
- `TileWindmillBlade.setEnergy` takes a `double` (the original took an `int` for a double field).
- Flywheel controller re-reads its redstone signal when placed (the original only at the next neighbour change); the
  controller's `powered` flag is also marked dirty.
- Kept as in the original, on purpose: the flywheel `torqueLoss` that `balancePower` adds a second time (display only), the
  `epsilonEquals`/lerp animation arithmetic, the integer division in the flywheel storage client lerp, the unfixed
  `clientEnergy` keys of the hand crank.

## Wiring needed in shared files (the base slice / orchestrator)

1. **Registry class** (the base slice's init class, e.g. `init/AwAutomationTorque`), with the names below. Use qualified static
   references inside the lambdas (`AwAutomationTorque.X_BE.get()`) to avoid illegal forward references.
   ```java
   // per tier t in LIGHT, MEDIUM, HEAVY (suffix _light, _medium, _heavy); props = BlockTorqueBase.defaultProperties()
   TORQUE_SHAFT_X       = REG.block("torque_shaft_x",       p -> new BlockTorqueTransportShaft(p, TorqueTier.X, () -> AwAutomationTorque.TORQUE_SHAFT_X_BE.get()), BlockTorqueBase.defaultProperties());
   TORQUE_SHAFT_X_BE    = REG.blockEntity("torque_shaft_x", TileTorqueShaftX::new, TORQUE_SHAFT_X);          // 1.12.2 id torque_shaft_x_tile
   TORQUE_JUNCTION_X    = ... new BlockTorqueJunction(p, TorqueTier.X, () -> ..._BE.get())    BE: TileConduitX::new        (id torque_junction_x_tile)
   TORQUE_DISTRIBUTOR_X = ... new BlockTorqueDistributor(p, TorqueTier.X, ...)                BE: TileDistributorX::new    (id torque_distributor_x_tile)
   FLYWHEEL_CONTROLLER_X = ... new BlockFlywheelController(p, TorqueTier.X, ...)              BE: TileFlywheelControllerX::new (1.12.2 ids flywheel_light_tile, flywheel_medium_tile, flywheel_large_tile)
   FLYWHEEL_STORAGE_X   = ... new BlockFlywheelStorage(p, TorqueTier.X, () -> AwAutomationTorque.FLYWHEEL_STORAGE_BE.get()), BlockFlywheelStorage.defaultProperties()
   // one block entity type shared by the three storage blocks:
   FLYWHEEL_STORAGE_BE  = REG.blockEntity("flywheel_storage", TileFlywheelStorage::new, FLYWHEEL_STORAGE_LIGHT, FLYWHEEL_STORAGE_MEDIUM, FLYWHEEL_STORAGE_HEAVY);
   HAND_CRANKED_GENERATOR = REG.block("hand_cranked_generator", p -> new BlockHandCrankedGenerator(p, () -> ..._BE.get()), BlockTorqueBase.defaultProperties());  BE TileHandCrankedGenerator::new
   STIRLING_GENERATOR     = ... new BlockStirlingGenerator(p, ...)     BE TileStirlingGenerator::new      (id stirling_generator_tile)
   WATERWHEEL_GENERATOR   = ... new BlockWaterwheelGenerator(p, ...)   BE TileWaterwheelGenerator::new    (id waterwheel_generator_tile)
   WINDMILL_GENERATOR     = ... new BlockWindmillGenerator(p, ...)     BE TileWindmillController::new     (id windmill_generator_tile)
   WINDMILL_BLADE         = REG.block("windmill_blade", p -> new BlockWindmillBlade(p, () -> ..._BE.get()), BlockWindmillBlade.defaultProperties());  BE TileWindmillBlade::new (id windmill_blade_tile)
   ```
   That is 20 blocks and 18 block entity types. All block items are plain `BlockItem`s from `REG.block`
   (the 1.12.2 `ItemBlockTorqueTile` is not needed: facing and owner are set by the block).
2. **Capabilities** (mod-bus `RegisterCapabilitiesEvent` listener): for each of the 17 torque block entity types except the
   flywheel storage and windmill blade, `TorqueCapabilities.register(event, TYPE.get());` (adds `AwCapabilities.TORQUE` and
   `Capabilities.EnergyStorage.BLOCK`); and `TorqueCapabilities.registerStirling(event, STIRLING_GENERATOR_BE.get());`
   (item handler on every side). Types to register: 3 shafts, 3 conduits, 3 distributors, 3 flywheel controllers, hand crank,
   stirling, waterwheel, windmill controller.
3. **Stirling menu**: the GUI slice calls `TileStirlingGenerator.setMenuFactory((id, inventory, generator) -> new StirlingMenu(...))`
   (from common setup). The menu reads `getFuelHandler()`, `getBurnTime()`, `getBurnTimeBase()`; the client menu opens with the
   block position written by `onBlockClicked` (`buf.writeBlockPos`).
4. **Config** (`AWAutomationStatics`, already ported): the slice reads `low/med/high_efficiency_factor`,
   `low/med/high_transfer_max`, `low/med/high_storage_energy_max`, `stirling_generator_output`, `waterwheel_generator_output`,
   `hand_cranked_generator_output`, `windmill_per_size_output`, `rpmToRpt`, `low_rpt`, `torqueToRf`, `rfToTorque`,
   `energyMinNetworkUpdateFrequency`, `enable_energy_network_updates`, plus `AWCoreStatics.energyPerWorkUnit`.
5. **Lang**: merge `port-notes/automation-torque.lang.json` into `assets/ancientwarfareautomation/lang/en_us.json`.
6. **Tags**: add the 20 blocks to `data/minecraft/tags/block/mineable/pickaxe.json` (1.12.2 `Material.ROCK`; the blade is wood,
   use `mineable/axe`). `defaultProperties()` does not call `requiresCorrectToolForDrops()`, so without the tag the blocks
   still drop (slower to mine). Add `requiresCorrectToolForDrops()` to the properties if the original "needs a pickaxe" is wanted.
   The research recipes use `ancientwarfare:torque_shafts/{wooden,iron,steel}` (defined by Core's data) and two groups that no
   tag file in the repo defines yet: `c:gears/{wooden,iron,steel}` (Core's gear set items) and `c:ingots/steel`.
7. **Renderer slice** (client): block entity renderers for the 18 types. What they read:
   - all torque tiles: `getPrimaryFacing()`, `getClientOutputRotation(side, partialTicks)` (radians), `getRenderBounds()`
   - `TileTorqueSidedCell` (junction, distributor): `getConnections()` / `isConnected(side)`
   - `TileTorqueShaft`: `hasPrevious()`, `hasNext()`; `TileTorqueSingleCell`/`SidedCell`: `getClientEnergyState()`
   - `TileFlywheelController`: `getFlywheelRotation(partialTicks)`, `isPowered()`, `getClientOutputRotation(UP-side input via useOutputRotation)`
   - `TileHandCrankedGenerator`: `getCrankRotation(partialTicks)`; `TileWaterwheelGenerator`: `wheelRotation`, `isValidSetup()`, `getRotationDirection()`
   - `TileFlywheelStorage`: `isControl`, `setWidth`, `setHeight`, `getRotation(partialTicks)`, `getClientEnergyPercent()`, `getRenderBounds()`
   - `TileWindmillBlade`: `isControl()`, `getWindmillSize()`, `getDirection()`, `getRotation(partialTicks)`, `getRenderBounds()`
   The 1.12.2 render bounds are now `getRenderBounds()` on the tiles; the renderer returns them from `getRenderBoundingBox(BlockEntity)`.
   The block render layers (flywheel storage solid + translucent, windmill blade not rendered as a full model) and the render shape
   (`ENTITYBLOCK_ANIMATED` once a renderer draws the block) are renderer-slice decisions; the block classes use the defaults.
   The placeholder models in the assets are plain cubes and should be replaced.
8. Nothing else in shared files. `AwClient`/`AwNetwork` need nothing from this slice (no payloads).

## Not ported (and why)

- Everything CodeChickenLib: `registerClient`, `getBakery`, `getExtendedState`, `IBakeryProvider`, block key generators, state
  mappers, `AutomationProperties` (the 14 unlisted properties) and the connection properties: renderer slice. The block state
  has only `facing` (and `valid_setup` for the waterwheel).
- `BlockBaseAutomation` (creative tab and client registration): the registrar does both. `ItemBlockTorqueTile` (replaced by the
  block's `getStateForPlacement` / `setPlacedBy`). `RFProxy`, `RFProxyActual`, `@Optional` RF interfaces (replaced by FE).
- `getSubBlocks`, `damageDropped`, `getMetaFromState` etc.: gone with metadata. `isOpaqueCube`/`isNormalCube`/`isFullCube`/
  `isSideSolid`/`shouldSideBeRendered`: `noOcclusion()` in `defaultProperties()` plus the support shape of the flywheel
  controller (`isSideSolid` true); the rest of `isSideSolid` false is the default for non-full shapes.
- `.m2f` models (custom format, cannot be loaded); the OBJ models are copied unchanged.
- The stirling menu and screen (GUI slice; only the opening hook exists).
- Placing a blade or flywheel storage block by anything that does not call `setPlacedBy` (structure templates, commands) does not
  validate until a neighbour is placed or broken; the original behaved the same way with `onBlockPlacedBy`.

## Unconfirmed API (not seen in the 1.21.1 sources beyond another slice's use)

- `ServerPlayer#openMenu(MenuProvider, Consumer<RegistryFriendlyByteBuf>)` (as Core's `ResearchStationBlockEntity` uses it).
- `BlockEntity#setBlockState` is deprecated in 1.21.1 but overridable and is called by `LevelChunk` when the state of an existing
  block entity changes (read in `LevelChunk.setBlockState`); relied on to clear the neighbour cache when the hammer turns a block.
- The `AWAutomationStatics` field names (taken from the config slice's file as it exists now).

## Rework candidates (not done, for step 4)

- Real block entity renderers with the rotating parts; decide full animation or static models first.
- `TileTorqueBase`'s inner FE adapter duplicates `worksite/TorqueEnergyStorage` (same maths): unify (the worksite class could take
  the side-null check, or the torque tiles could use it).
- The three tier classes per tile type could become one class with a tier taken from the block (`ITieredBlock`), if the shaft chain
  test compares tiers instead of classes.
- Neighbour discovery could use `BlockCapabilityCache<ITorqueTile, Direction>` instead of the hand-invalidated cache.
- Push order dependence: transfer between tiles still depends on tile tick order (open question 5 of report 05); unchanged.
- Windmill: no wind, weather or height; no upper size limit despite the comment (17). Flywheel: the extra `torqueLoss` add
  (display only). Config options `*_conduit_energy_max` and `enable_energy_client_updates` are still never read.
- Hand crank: the `clientInputEnergy` / `clientInputDestEnergy` key naming in the save tag is inconsistent (kept for old saves).
- Connections as real block state properties (vanilla pipe style) would give models the connection flags without a renderer.
